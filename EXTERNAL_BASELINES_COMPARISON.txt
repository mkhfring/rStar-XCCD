2b. THE TEXT-EMBEDDING-3-LARGE BASELINE -- BEATS EVERYTHING IN THIS PROJECT
--------------------------------------------------------------------------------
CORRECTION to an assumption in section 1: the CLCCD paper's stated
"GraphCodeBERT" and "UniXcoder" baselines are NOT reproduced anywhere in
this repo (grepped for both names, only a coincidental substring hit in an
unrelated SVG file) -- the paper appears to cite those two from other work
rather than re-running them. The one non-LLM baseline this repo actually
implements is OpenAI's `text-embedding-3-large` (get_embeddings.py) +
classifier/classifier.py, an SVM/KNN on top of the frozen embeddings.

Their own checked-in results (classifier/data/ada_java_{cn,xl}.txt) pool
ALL language pairs together in one 80/20 split (SVM/KNN, F1 0.97-1.00) --
not a python-specific number. But classifier/data/ada_java_{cn,xl}.json
already contain the raw per-record embeddings AND a precomputed cosine
similarity ("Result") with the ll2 label intact, so a python/rust-specific
number can be pulled out directly, without re-calling the OpenAI API.

Recomputed here with the SAME methodology as this project's own
GRAPHCODEBERT_CLCCD_BASELINE.md (cosine-similarity threshold, calibrated on
an 80% dev split, reported on the held-out 20% test split, no fine-tuning of
the embedding model itself) -- pooling codenet+xlcost for Python (n=1800,
same population as section 2's java comparison), codenet only for Rust
(n=600, java-rust, same non-comparability caveat as section 2):

  text-embedding-3-large + threshold        F1       Precision  Recall
  ll2=Python (java-python, n=1800, test=360) 0.9728   0.9944     0.9521
  ll2=Rust   (java-rust,  n=600,  test=120)  0.9219   0.9365     0.9077

0.9728 on java-python beats every model in this entire project, including
the best pure-inference (Qwen3-8B, 0.9559) and the best MCTS result
(Qwen2.5-Coder-7B code2-exec v2, 0.9541) -- and by a wide margin beats this
project's own from-scratch GraphCodeBERT-base baseline (java F1 0.7257,
GRAPHCODEBERT_CLCCD_BASELINE.md).

CORRECTION (2026-09-13): an earlier draft of this section attributed the
gap over GraphCodeBERT-base to text-embedding-3-large being "a much larger,
more capable embedding model." That is NOT a verified fact -- OpenAI has
never publicly disclosed a parameter count for text-embedding-3-large (only
that it outputs 3072-dim embeddings and is the larger of their two current
embedding tiers). Checked via web search before writing this correction; no
official or credibly-sourced parameter count exists. Do not restate the
size claim as fact elsewhere without a real source.

What can be stated without needing that unverified claim: a frozen,
commercially-served text embedding plus a simple calibrated threshold is,
on this exact 1800-row java-python population, a stronger clone detector
than any prompted or searched LLM tried in this project so far -- this is
the same population section 2 already scores every LLM on, so the
comparison is apples-to-apples, not an artifact of a different test set.
WHY it wins (model size, training data, embedding-vs-generative-prompting
as a task formulation, or something else) is not something this project's
data can actually distinguish, and should not be attributed to size without
a source.

4a. RESPONSE RATE -- THE REASONING PROMPTS HAVE A REAL, SEVERE GAP
--------------------------------------------------------------------------------
Response rate = judged / total (the intuitive sense, NOT the inverted
"no-judgment/total" label used inside individual _result.txt files
elsewhere in this project). Parsing: first standalone "yes"/"no" in the
raw generation for sp1/sp2/reas/inte/sl; first number, thresholded at >=5,
for sim.

Direct-answer prompts (sp1, sp2, sim) essentially never fail to parse:

  prompt   response rate range across all 4 models x 2 datasets
  sp1      0.9994 -- 1.0000
  sp2      1.0000 always
  sim      0.9983 -- 1.0000

Reasoning-first prompts (reas, inte, sl -- each asks the model to reason
BEFORE concluding) fail to parse far more often, and the gap is severe in
the worst cases:

  prompt   response rate range across all 4 models x 2 datasets
  reas     0.4733 -- 1.0000
  inte     0.5517 -- 0.9822
  sl       0.3150 -- 0.9808

Worst case: Qwen2.5-Coder-3B, rust, prompt "sl" -- response rate 0.3150,
i.e. 822 of 1200 samples got NO judgment at all. Second-worst: Qwen2.5-
Coder-7B, rust, prompt "reas" -- response rate 0.4733 (632/1200 no-
judgment). This pattern holds across every model tested: asking for
reasoning before a verdict trades away a large chunk of parseable answers,
consistent with max_tokens=768 cutting the response off before it reaches
a stated "yes"/"no" on the more verbose reasoning path. Direct-answer
prompts never show this failure mode.

Related but NOT separately measured: on the samples that DO get judged
under reas/inte/sl, recall is often lower than under sp1/sp2 for the same
model -- consistent with (not proven by) a second, distinct risk in the
parser: it takes the FIRST "yes"/"no" anywhere in the response, and
reasoning text that explores "is this a simple yes or no" before its real
conclusion can get mis-parsed from a mid-reasoning word rather than the
model's actual verdict. Raw generations are preserved in the output files
specifically so this could be re-parsed later without rerunning inference,
but that has NOT been done -- this paragraph is a flagged risk, not a
measured one.
