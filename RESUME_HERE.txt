1. WHAT THE EXPERIMENT IS
--------------------------------------------------------------------------------
The Code-2-execution change (stage_code2() in rstar_deepthink/tools/python_tool.py)
lets the MCTS search compile and RUN the second code snippet (Java/Rust) instead
of only reasoning about its expected output. Question: does that recover clone
pairs the models previously got wrong?

Retry dataset = samples BOTH Qwen2.5-Coder-7B and Qwen3-8B got wrong in the
final-for-clccd runs (built by rstar-xccd/build_failed_dataset.py):
    eval_data/failed_both_python_java_CLCCD.jsonl   45 samples (all FN on true clones)
    eval_data/failed_both_python_rust_CLCCD.jsonl   20 samples (19 FN + 1 FP)
Baseline is 0/65 correct BY CONSTRUCTION, so any correct answer is a recovery.

CAVEAT THAT MATTERS: the set is 98% ground-truth "clone", so ANY drift toward
answering "clone" scores well here while potentially destroying precision on the
full 1800/1200. This subset cannot measure precision. Also temperature=0.7, so
part of any gain is rerun variance (no control run has been done).

The v1 finding "when Code 2 ran, accuracy was 84.6% vs 33.8%, p=0.0013" was a

Starting point: section 3e's rust precision problem (item 7e). Diagnosis of
individual v2 rust false positives (idx 24/27/28 of the retry set) found the
model settling for 1-2 small, round, self-picked test inputs that happened to

right. Root cause looked like: weak/narrow self-generated tests.

FIX ATTEMPT 1 (prompt-only, branch code2-exec-rust-testfix-v1):
New few_shot_code2_exec_python_rust_v3.json / mcts_prompt_code2_exec_python_
rust_v3.json. Added rule 13/14: require >=3 structurally different test
inputs (boundary/degenerate, small, larger-or-differently-shaped) before
trusting an execution match as clone evidence. New 3rd few-shot example: a
single-digit test matches by coincidence, a multi-digit test exposes a real
off-by-one bug -- verified for real (compiled + ran both snippets, got 0/0
then 25/9) before use. num_few_shot bumped 2->3 so the new example is never
sampled out.

RETRY-SET RESULT (job 2895234, 118-sample failed_rust_v2_CLCCD.jsonl = every
sample the full v2 rust run got wrong): 78/118 (66%) now correct. Broken down
by original failure kind: FP 55/78 recovered, FN 20/37 recovered, no-judgment
3/3 resolved. Looked like a clear win -- splicing this into the untouched
1082 v2-correct samples projected F1 .9340, beating pure inference (.8893).

FULL-DATASET RESULT (job 2899116, all 1200 rust questions, CANCELLED at
980/1200 by explicit request once the pattern below was confirmed): the
splice projection was WRONG. On the same 980 indices, v2 scored F1 .8083,
v3-fix scored F1 .7707 -- WORSE, not better. Diffing predictions index-by-
index: 65 regressions (v2 correct -> v3 wrong) vs only 49 recoveries in the
first 699 rows, widening to 91 regressions vs 65 recoveries by 910 rows. The
retry-only test structurally could not see this, since it excluded every
sample v2 already got right by definition -- exactly the caveat flagged when
the splice projection was first given.

ROOT CAUSE, TRACED TWO LAYERS DEEP (both are real bugs, both now fixed):

(1) SCORING BUG in evaluate_clone_results.py predict_label(). The
    exec-signature override (forces "clone" whenever no_code/blocked/
    assertion_failed appears anywhere in the tree) was checked BEFORE
    reading leaf votes, and returned unconditionally -- overriding a real,
    often-unanimous, often-correct leaf verdict, not just filling in a
    no-judgment gap as its own comment claimed. Measured: on v2, 191/192
    override firings had real leaf votes behind them anyway (only 1 was
    genuinely no-judgment), and leaf-votes-alone would have scored 81.8% vs
    the override's 78.1% on exactly those trees -- the override was already
    net-negative on v2, not just on v3. On v3 it got much worse (81.6% vs
    64.8%) because v3's own >=3-diverse-inputs rule raises the no_code rate
    (14.7%->20.0% on the same 980 rows), firing the override more often.
    FIX: moved the check to only apply when votes is empty (restores the
    invariant the original comment described). Verified: v2 full-dataset F1
    0.8189->0.8243 (also improves the ALREADY-PUBLISHED section-3e numbers).
    v3-fix on the 980 covered rows: F1 0.7692->0.8154, nearly erasing the
    apparent regression on its own.

(2) HARNESS BUG in rstar_deepthink/agents/mcts.py create_child(). When a
    code step is cut off before its closing <end_of_code> tag (more likely
    under v3, which asks for longer, multi-input test blocks), the harness
    DOES execute the truncated fragment and gets a real observation -- but
    only appends it to state["text"] (so the model can see it) when
    CODE_END is present. When it isn't, the observation is silently
    dropped, the model has no idea whether its code ran, and there is no
    penalty either: "No valid Python code found in the response." does not
    contain the word "error", so code_ran_ok was True and
    consecutive_errors never incremented. PROVEN, not just inferred: at
    idx 90 of job 2899116, node 0.2.1.1 has no observation and no
    exec_outcome (a dropped truncated step), and its two SIBLING children
    (same never-executed continuation, sampled twice) independently
    fabricated two different, mutually contradictory "<output>" blocks with
    made-up numbers -- one claiming a match (wrong, truth is non-clone),
    one claiming a mismatch (right). A real harness observation would be
    identical across siblings; these weren't, so they were invented.
    FIX: create_child() now always appends the (wrapped) observation to
    state["text"], and code_ran_ok now also treats NO_CODE_MESSAGE as a
    failure, so it counts toward errors_threshold like any other crash.
    This is a repo-wide change (affects every PoT config, not just this
    experiment) -- has NOT yet been validated on anything but the rust
    combined retry set below; watch for side effects on unrelated configs.

4. THE LD_PRELOAD BUG (found + fixed 2026-09-08, uncommitted)
--------------------------------------------------------------------------------
The slurm scripts export LD_PRELOAD=libnccl.so.2 for vLLM. rustc inherits it when
it shells out to link; that shell is an old glibc-2.24 nix build that cannot meet
libnccl's GLIBC_2.34 requirement, so EVERY rustc call died with
  "error: linking with `cc` failed: exit status: 1"
javac is unaffected (not a cc wrapper) -- which is why Java always worked and
Rust NEVER compiled, in any run, including the original harness commit.

FIX: _compiler_env() in rstar_deepthink/tools/python_tool.py returns os.environ
minus LD_PRELOAD; both the javac and rustc subprocess.run() calls in stage_code2()
now pass env=_compiler_env().

VERIFIED with LD_PRELOAD actually set, over all 20 rust failure samples:
    compiled OK 0 -> 13 ; declined (real external crates) 7 ; still failing 0
The 7 declines are legitimate: proconio / itertools / petgraph need network.
Safe because vLLM already dlopened NCCL at start-up, and running the compiled
binary / python3 / java under LD_PRELOAD was verified fine -- only the COMPILE
step needed it stripped.


5. HOW TO SCORE THE RESULTS
--------------------------------------------------------------------------------
cd /lustre06/project/6104180/khajezad/rstar-xccd-remote/rStar-XCCD/rstar-xccd
source ../venv/bin/activate          # venv-qwen3 for Qwen3 models
python - <<'PY'
import json, glob, re, sys
sys.path.insert(0,'.')
from evaluate_clone_results import predict_label          # frozen CLCCD config
for tag in ("fewshot.","fewshot-v2.","ldpreload-fix."):
    for f in sorted(glob.glob(f"eval_data/failed_both_python_*code2-exec-{'lang-' if 'fewshot' in tag else ''}{tag}*.jsonl")):
        if f.endswith("_result"): continue
        n=ok=comp=0
        for line in open(f,encoding='utf-8'):
            line=line.strip()
            if not line: continue
            r=json.loads(line)
            if "question" not in r: continue
            n+=1
            obs=[(x.get("observation") or "") for x in r["rstar"].values() if isinstance(x,dict)]
            if any("compiled" in o for o in obs): comp+=1
            if predict_label(r["rstar"])==(r.get("answer") or "").lower(): ok+=1
        print(f"{n:>4} {ok:>4} correct {comp:>4} C2-compiled  {f.split('.mcts.')[1][:70]}")
PY
